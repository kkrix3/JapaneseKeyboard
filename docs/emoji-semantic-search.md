# 日本語による絵文字の意味検索

基点は `preview` の `e3cc93537c1c0912cb451b39133c270d39a10b9b`。作業先は `feature/emoji-semantic-search`、Draft PRは https://github.com/kkrix3/JapaneseKeyboard/pull/12 。通常入力を維持するため、検索用の入力状態をIMEの変換状態・アプリのInputConnectionから分離した。検索を使わないときは検索データを読み込まない。

## データ・ライセンス・互換性

- CLDR 48.2の日本語 `annotations` / `annotationsDerived`：正式名称・キーワード。Unicode-3.0。固定XMLとハッシュを `tools/emoji_search/upstream/` / `manifest.json` に保存した。完全な著作権・許諾文をAPK内 `emoji_search/NOTICE.txt` に同梱する。再配布・改変はその表示を保持する条件で可能。出典：https://github.com/unicode-org/cldr/tree/release-48-2 、ライセンス：https://www.unicode.org/license.txt 。
- 既存の絵文字辞書の読み：同梱LOUDSとトークン配列から再現可能なJDKツールで抽出。独立したアプリ側テストで実際の読込経路と照合する。
- Sumire独自の用途辞書：73概念。感謝・応援・謝罪・安心・お祝い・内緒・疲れ・困惑などの用途と同義語・かな表記をJSONで管理。MIT。個別クエリの順位や固定結果リストは実装しない。
- カテゴリ・順序：既存のUnicode Emoji 17.0メタデータを使用。

実収録は **1,902種類**。すべてにCLDR名称が対応する。先行調査と同じ構成（カテゴリメタデータ×CLDR、肌色を除外、表示セレクタを統合）を固定48.2で再構成すると1,914種類。共通1,898、調査側だけ16（新しい絵文字や旗）、実収録側だけ4（🦰 🦱 🦲 🦳）。従って単純な同一母集団比較ではない。

NFKC、英字の小文字化、カタカナ→ひらがな、空白・軽い句読点の除去を検索語に適用する。照合IDはコードポイント列からFE0E/FE0Fと肌色だけを除去し、ZWJ、性別、方向、複合列の順序は保持する。表示・入力文字列は実行時の収録リストから取り、正規化文字列をcommitしない。検索結果の肌色は従来の `EmojiSkinToneSupport` を通す。CLDRの肌色付き派生注釈はベース名称・キーワードへ混ぜず、正式なベース名称を保持する。検索メタデータに存在するだけの絵文字を候補に追加しない。

## 順位付け

1. 絵文字自体の一致：1,600。
2. 名称の完全一致：1,200、用途・同義語：1,100、CLDRキーワード・既存の読み：1,000、関連用途：800、カテゴリ：600。
3. 前方一致は完全一致から300、語内部分一致は500を減点。自然文中の登録語の一致は語長・クエリの被覆率を考慮する。短いかなの偶然一致を抑える。
4. 複数の明示的な空白区切り語は、すべてに一致する候補だけを採用する。裏付けの加点は最大30。同点は既存の収録順。履歴・頻度で関連度を上書きしない。
5. 最上位スコアの60%未満の弱い候補を除く。IDで重複を抑え、関連候補が少ない場合は5件を埋めない。

走査は全1,902件。UIから50msのデバウンスを経てワーカーで実行する。新しい入力では旧Jobを取り消し、世代番号とコルーチンの取消を確認してから表示する。入力直後に旧結果を消し、別クエリの候補を誤タップしないようにする。履歴を使った穴埋めはしない。

## UIとIMEの入力保護

絵文字モードの「絵文字を意味で検索」から開始する。検索欄は編集可能なEditTextではなくTextViewであり、専用のかなパネルが私有バッファを編集する。フリック、長押しでの文字選択、濁点・半濁点・小書き変更に対応する。かなの読みでも検索でき、IMEのかな漢字変換や別のIMEを再帰起動しない。今回のパネルでは漢字変換・ローマ字変換・自由なカーソル編集は提供しない。

- 検索の開閉・入力・消去で、アプリのテキスト、カーソル、未確定範囲を操作しない。
- 検索中の削除は私有クエリだけを削除。長押しは全消去。キャンセルでは削除しない。
- 戻るは文字選択ポップアップ→かなパネル→検索画面の順に閉じる。検索内の戻るボタンは通常一覧へ復帰。Android 13以降のBack callbackと、物理キーのdown/up両方を扱う。
- 検索結果タップは既存の絵文字commit・履歴保存と同じ経路。長押しの肌色選択も既存経路を使う。検索文字列は履歴に保存しない。
- カテゴリ・履歴・絵文字以外のモードを維持する。モード切替、入力セッション終了、画面再生成・回転では検索を閉じ、古い結果を破棄する。
- 通常入力の処理より前に、検索対象の物理入力だけを受け止める。検索を閉じた後に余ったkeyupがアプリへ流れないようにする。

Google絵文字表示切替や新しいフォントには依存せず、既存の絵文字描画・入力文字列を使用する。Android 14のフォントが新しいUnicodeグリフを表示できるかは既存の表示環境に従う。

主な失敗：

- 「心から感謝しています」の🈯️は「してい」という既存の読みの偶然一致。登録語との表面的な重なりが感謝の意味を上回る場合がある。
- 「ちょっと一息つこう」→🤏・1️⃣、「今日は土砂降り」→⌛️・⏳️は短い語・漢字の偶然一致であり、上位に無関係な絵文字が出る実例として残す。
- 「気分は最高」「試験に受かったよ」「そろそろ寝よう」などは、同義関係・活用・文脈が辞書に登録されていなければ見つからない。
- 「感激で胸がいっぱい」の🥲は文脈上妥当でも固定代表正解に含まれず未命中。「月がきれいだね」は月の系列から候補を拾えるが、語用や含意は理解しない。
- 否定、皮肉、多義語、複数の出来事の合成は解釈しない。「辞書にない自然文の意味理解」を保証しない。

## 性能・検証

検索用TSV **270,098 bytes**、許諾文 **2,352 bytes**。ホストのdeflate level 6では合計約77KB（APK増分の実測とは区別）。元XMLや評価ツールはAPKへ含めない。モデル・ベクトル・追加推論runtimeは0。

Linux x86_64 / OpenJDK 17 / Kotlin 2.2.10で製品のKotlinを実行。予熱後、76クエリ×20回。保持ヒープはGC後の差分なので、正確なAndroid PSSやアプリ全体の常駐量ではない。測定スクリプト・環境・生データを保存した。

独立した3 JVM起動の中央値：検索p50 **0.337ms**、p95 **0.511ms**、p99 **0.908ms**、検索repository生成 **26.2ms**、保持ヒープ増分 **1,071,000 bytes**、一時割当 **3,128 bytes/query**。通常キーボード初期化時にはasset読込を行わず、最初に検索を開いた時だけI/Oワーカーで読み込む。Android 14エミュレータの検索時間・PSS診断値・APKの比較結果はPR #12の検証記録に記載する。Android実機の初期化時間・電力・温度は未測定。

検索エンジンのホストJUnitは6件、CLDR生成処理のPythonテストは2件成功。実データ再生成はバイト単位で一致。実収録集合の評価、API 28/34の入力保護、非表示・削除押下中の移行に回帰テストを追加した。Android 14の実IME試験と既存Full Preview CIの最終run・検証対象SHA・失敗や未検証事項は [PR #12の検証記録](https://github.com/kkrix3/JapaneseKeyboard/pull/12) を参照する。単体テストの成功を実機試験の成功として扱わない。

署名済みFull Previewの既存ワークフローは `refs/heads/preview` での所有者の手動起動に限定されている。この作業ブランチからは条件を満たさないため、署名条件や鍵の設定は変更しない。生成されるunsigned Preview APKはそのままインストールできない。

インストールして確認するための別IDのDebug検証版は、[Emoji Search Android 14](https://github.com/kkrix3/JapaneseKeyboard/actions/workflows/emoji-search-ci.yml) の成功runにある `emoji-search-debug-testbench` から取得する。APKと`metadata.json`を同梱し、実際にAPI 34へインストールした同一APKの署名・ID・検索asset・ARM64/x86_64のライブラリを検査する。IDは `com.kazumaproject.markdownhelperkeyboard.preview.testbench`。CI生成のDebug証明書を使い、通常のSumire/Previewとは別パッケージである。ARM64は同梱確認であり、Android 14実機での動作測定を意味しない。通常の非debug Full Preview unsigned APKは既存Preview CIのartifactを使う。取得先runとSHA-256はPRに記録する。

## 主な変更箇所と将来の接続

- `symbol_keyboard/.../emoji/search/EmojiSearchRepository.kt`：検索メタデータと実収録集合の対応。Readerを受け、Androidに依存しない。
- `EmojiSearchEngine.kt`：順位付きの `EmojiSearchResult` を返すインターフェイスと辞書実装。
- `EmojiSearchNormalizer.kt` / `EmojiSearchInputState.kt`：照合IDとローカル入力バッファ。
- `EmojiSearchInputView.kt` / `CustomSymbolKeyboardView.kt` / レイアウト・日英リソース：検索UI、キャンセルと世代管理、肌色・通常表示との接続。
- `IMEService.kt`：検索中の物理入力・戻る・セッション終了だけを接続。
- `tools/emoji_search/`：出典、生成、評価、再現手順。
- `EmojiSearchEngineTest` / `BundledEmojiSearchTest` / `IndependentEmojiSearchUiTest` / `EmojiSearchImeDeviceTest`：検索・収録整合性・入力保護・実IME試験。
- `.github/workflows/emoji-search-ci.yml`：既存CIで未実行だったsymbolテストとAndroid 14用の追加検証。既存Preview署名・通常CIは変更しない。

E5を追加する場合は `EmojiSearchEngine` の別実装が同じidentity/symbol/name/scoreの結果を返す。UIの入力・結果表示・取消処理は再利用し、repositoryのidentityをベクトルindexの識別子に使う。モデルhash・前処理・tokenizer・indexの対応、取消・別ワーカー、候補の実収録フィルタは追加側で保証する。

辞書方式が実用的なのは、対象が比較的定まった名称・読み・短い用途語で、同義語を保守できる場合。未知の言い換え、活用した自然文、含意、文脈をまたぐ意味の接近を広く扱う場合はEmbeddingなどの候補生成が必要になる。否定や皮肉までEmbeddingだけで解決すると約束せず、別途品質評価が必要。
