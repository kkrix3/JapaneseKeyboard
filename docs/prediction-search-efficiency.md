# 通常辞書予測の探索効率改善

基点は本家dev `df1f38315bf56d860d32919a3eaed6a75499e91e`（v1.7.132）。fork/devの独自コミットが0件、170コミット遅れであることを確認し、forceなしで同期した。

## 変更と候補の互換性

標準辞書と追加ユーザー辞書の通常予測について、日本語予測OFF、正規化後の最小入力長未満、16文字超を探索前に除外する。読み長の上限は従来どおり「入力長＋正規化後の先読み文字数」で、UTF-16のコード単位を数える。上限に到達したノードの終端は収集するが、その子へ降りない。

DFSの終端順、読みから候補を作る順、候補の全フィールドとペナルティ、標準辞書→追加ユーザー辞書の順、安定ソートと最終件数を維持する。先着候補による打切りは行わない。絵文字・記号の完全一致経路、分類別辞書、小さい補助辞書の経路や設定は変更しない。

コルーチンのContextを要求から引き継ぎ、探索は64ノードごと、候補作成は64読み／64トークンごと、および処理境界でensureActiveを呼ぶ。例外を捕捉して空結果へ置換しない。呼出し先の変換セッションとIME候補更新もCancellationExceptionを再送出する。ソートは従来の実装を維持し、その前後で取消を確認するため、ソート自体を途中中断する変更ではない。

## PCでの測定

Linux x86-64、AMD EPYC 9V74、OpenJDK 17.0.20、Kotlin 2.3.21、kotlinx-coroutines 1.10.2。同じ同梱辞書をPacked配列として読み込み、同じ入力・設定・JVM引数で比較した。ウォームアップ後、独立した3回のJVM起動で順序を交替し、各起動の中央値をさらに中央値で集計した。

| 入力・入力列 | 改修前 | 改修後 | 一時割り当て（前→後） |
| --- | ---: | ---: | ---: |
| こう（最小入力長未満） | 2.128 ms | 0.00049 ms | 556.2→0.016 KiB |
| しょう | 3.649 ms | 2.585 ms | 2387.5→2100.6 KiB |
| にほん | 0.981 ms | 0.396 ms | 292.1→198.0 KiB |
| 30句353要求・予測ON | 63.872 ms | 24.709 ms | 23.98→14.53 MB |
| 同じ353要求・予測OFF | 40.200 ms | 0.031 ms | 10.02→0.006 MB |

353要求では時間約61%、割り当て約39%の削減。これは予測部分の合計であり、入力・変換・描画全体の速度向上率ではない。割り当ては測定スレッドが作った一時オブジェクトの累積で、常駐RAMの削減量ではない。CPU時間とp95は生ログに記録している。

改修前は、同期した本家の3メソッドを変更せず抜粋した`OriginalPrediction.kt`を使用する。改修後は本番の`DictionaryPredictionSearch.kt`を直接コンパイルし、従来と同じソート・件数制限を行う。Engine全体のAndroid依存は含めない。候補クラスは本番のコードを使用し、使わない付加表示型3種だけを代替定義する。Android非依存の共通拡張関数も切り出している。実装用コードにこの代替定義は入らない。

固定入力、30句の構成入力列、実辞書から固定seedで抽出した160語の接頭辞、空・上限境界を合わせた846入力について、先読み1/3/6×予測ON/OFFの5,076条件で候補の全フィールドと順序が一致した。3起動とも同じ結果。追加ユーザー辞書の任意の内容を網羅する検証ではない。

再現方法（リポジトリのルートで実行）:

```sh
bash tools/prediction-efficiency/run.sh /path/to/gradle-9.6.0/lib /path/to/output
```

結果と環境・辞書SHA-256は`tools/prediction-efficiency/results/`を参照。必要なcompiler/stdlib/coroutinesはGradle配布物のlibを使用する。
